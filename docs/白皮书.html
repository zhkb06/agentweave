一、项目概述

1.1 一句话定位

织流 AgentWeave 是一个“以验证为中心”的多智能体编排、调度与可信验证平台：它不只让 Agent 跑起来，还要让每一次运行都可解释、可复现、可审计。

它不是又一个通用 Agent 应用市场，也不是聊天式工作流的包装；它解决的是 Agent 从演示走向交付时最容易被跳过的那一段工程问题——谁来决定任务派给谁、结果凭什么可信、失败之后系统如何自我修复。

1.2 背景：Agent 的“Demo 天花板”来自四类工程缺口

2025 年以来，大模型 Agent 的演示能力快速提升，但“演示能跑”与“业务敢用”之间仍有一道明显鸿沟。公开调研反复指向同一组事实：企业级 Agent 项目的失败率显著高于传统软件项目，多数生成式 AI 试点无法在财务口径上证明价值，原因往往不是模型不够强，而是工程约束缺位（相关公开数据见 6.1 来源说明）。我们把这类缺口收敛为四类：

缺口 典型表现 后果
编排缺口 流程写死在代码或提示词里，改一个步骤要改代码 流程不可版本化、不可审阅、无法由业务人员调整
调度缺口 任务分派靠串行、轮询或人工指定，缺能力画像与负载视角 慢任务拖垮整条链路，关键任务被饿死，决策无法解释
验证缺口 结果由模型自评“我做对了”，或仅做字符串/格式检查 错误结论带着“看起来专业”的格式进入交付物，错误被放大
自愈缺口 失败即终止，或无限重试烧预算 系统无法收敛，成本失控，失败原因无法沉淀

1.3 我们做了什么

围绕上述四类缺口，织流 AgentWeave 给出四件对应的工程能力，并全部做成可运行代码而非概念：

  1. 可编排：把工作流从代码里抽出来，变成声明式 JSON DSL（DAG + 节点类型 + 边条件），支持条件表达式、子工作流、人工闸门，流程本身可版本化、可审阅、可被引擎解释执行。
  2. 可调度：把“任务派给哪个 Agent”做成可解释的一等对象，内置五种调度策略（FIFO / 优先级 / 轮询 / 能力匹配 / 负载感知 / 自适应），每次决策输出分数、理由与负载快照，可按运行指定策略且策略之间互不污染。
  3. 可验证：把验证提升为与执行同级的流水线，内置 13 个检查器（结构、空值、数值真值、代码复算、交叉验证、统计检验、LLM 评审、产物存在性、数据质量、留出稳定性、多重共线性、显著性、不确定性），按威胁模型分四层漏斗执行，输出带权重与证据的置信度。
  4. 能自愈：把“检查—修复—再检查”做成 PDCA 自循环，带轮次预算与收敛判据；验证不通过时生成结构化反馈，驱动修复节点重跑，而非简单重试。

此外，平台提供事件总线（SSE 实时推送）、运行产物归档、可复现基准脚本与离线演示回放，使一次运行从“黑箱输出”变成“可回放的证据链”。

1.4 当前版本的边界（如实说明）

  • 默认使用 Mock 确定性模型，可离线复现，保证评审在断网环境下也能看到完整链路；接真实模型是可选配置项（OpenAI 兼容接口），尚未用真实 Key 完成端到端生产验证。
  • 演示数据为按公开公式与固定种子生成的合成数据（含隐藏真值文件，用于计算误差），不代表任何真实业务数据集。
  • 部署形态为单机单进程（Python 标准库 HTTP 服务 + JSON 文件持久化），面向演示与小规模试点，尚未做多租户、计量计费与高可用。

我们把这些边界写进方案书第十一章与本文 3.6 节，是因为“知道自己的边界在哪”本身就是可交付性的一部分。

二、解决方案

2.1 总体思路：把 Agent 系统当生产系统建设

项目的核心判断是：多智能体系统的主要矛盾已从“模型能不能完成任务”转移到“工程上能不能管住任务”。 因此我们把控制面（编排、调度、验证、循环、可观测）与执行面（模型调用、工具调用）分离，控制面用纯 Python 标准库实现且可单独测试，执行面通过统一 LLM 接口与工具注册表接入，二者以事件总线解耦。

2.2 六层架构

层次 职责 关键模块
接入层 HTTP API、SSE 事件流、静态前端 agentweave/api/
编排层 工作流 DSL 解析、DAG 校验、节点执行、条件求值 agentweave/workflow/
调度层 能力画像、负载均衡、优先级、策略决策与解释 agentweave/scheduler/
执行层 Agent 角色、工具注册表、LLM 适配（Mock / OpenAI 兼容） agentweave/agents/、agentweave/tools/、agentweave/llm/
验证层 检查器库、五层漏斗、置信度合成、反馈生成 agentweave/verify/
支撑层 运行状态、事件总线、持久化、配置与安全 agentweave/runtime/、agentweave/core/

2.3 七个 Agent 的岗位化定义

七个角色不是“人格扮演”，而是按“输入契约—输出契约—工具权限—成功判据”定义的岗位，每个岗位都有明确的权限边界：

角色 职责 典型工具权限
规划者 Planner 拆解任务、生成执行计划 只读：数据概览
数据工程师 DataEngineer 数据清洗、质量检查 读写：工作区数据
统计师 Statistician 统计建模与显著性判断 执行：受控代码沙箱
制图师 Visualizer 生成图表产物 写：artifacts
评审者 Critic 交叉验证、挑错 只读全部产物
校验者 Verifier 执行检查器、合成置信度 只读全部产物
写作 Agent Writer 汇总证据、生成报告 写：report.md

2.4 编排：声明式工作流 DSL

工作流是一份 JSON：nodes 定义任务节点（类型、Agent、输入映射、超时、重试），edges 定义依赖与条件，policies 定义预算与闸门。引擎负责拓扑校验、环检测、就绪节点推进、条件求值与失败传播。条件表达式不直接 eval，而是解析为受限 AST 后按白名单求值，杜绝表达式注入。人工闸门节点让关键步骤可以暂停等待人工确认，把“人在环路”做成流程的一部分而不是补丁。

2.5 调度：可被追问的决策

调度器对每个就绪节点计算综合得分：能力匹配度、当前负载、优先级、历史成功率（自适应权重）。决策不仅产出“派给谁”，还产出“为什么”：各分项得分、权重、候选快照与理由字符串，随运行事件与报告一起落盘。五种策略可按运行指定；为避免并发运行互相串改策略，每次运行 fork 一个独立调度器——策略隔离、统计共享，这样自适应学习的历史成功率能跨运行累积，而不会被单次运行私有化。

2.6 验证：换一种独立方式还能算出同一个结果

我们的验证哲学是：可信不是“模型说它对”，而是“换一种独立方式还能算出同一个结果”。 13 个检查器按五层执行：

  1. L1 结构与数据层：schema 契约校验、关键文本非空、产物存在性、数据集质量（行数/缺失/重复/离群）；
  2. L2 真值层：输出指标与数据集生成时已知的真值逐项比对，相对误差不超过容差（默认 15%）；
  3. L3 复算层：在子进程沙箱里独立重跑分析代码，比对重算指标与申报指标；
  4. L4 交叉层：由另一 Agent 不看申报结论、独立复算后比对，作为硬性通过条件；
  5. L5 统计与稳健层：显著性、置信区间、留出稳定性、多重共线性、统计阈值，以及可选的 LLM 结构化评审。

每个检查器返回通过/失败/证据，聚合为置信度；失败项生成结构化反馈（缺什么、差多少、建议怎么改），直接驱动自循环的修复节点。

2.7 自循环：带预算的 PDCA

自循环以“验证不通过”为触发条件，以轮次预算与收敛判据为边界：每轮执行修复节点、重跑验证、比较置信度增益，达到阈值或耗尽预算即停。这样系统既不会“一轮就放弃”，也不会“无限烧预算”，且每一轮的决策与证据都留在事件流里。

2.8 可观测性与运行形态

一次运行产生完整证据链：事件流（含每个节点的开始/结束/重试/失败、调度决策、验证结果、循环轮次）、产物目录（分析代码、图表、报告）、指标文件。前端提供编排台、运行看板、验证报告、系统配置等页面，运行过程通过 SSE 实时推送；同一运行可导出离线回放 HTML，便于评审在无环境时查看。

2.9 差异化定位

对比对象 它们的强项 我们的差异
LobeHub / Dify / Coze 等通用平台 生态、插件市场、低门槛搭建 我们不争通用编排生态，专注“执行后的可信与可审计”，验证层与调度解释是核心而非附件
DeepSeek Harness 等 Agent 运行时 工具调用与运行时能力 我们补的是编排之上的调度决策与多检查器验证漏斗，且强调零依赖可复现
自研脚本 + 提示词 灵活、成本低 流程不可版本化、无调度、无验证、无自愈，无法回答“为什么可信”

一句话：别人做“让 Agent 能干更多事”，我们做“让 Agent 干的事可被验收”。

三、应用成效

3.1 基准实测：三模式对照

项目内置基准脚本，对同一任务用三种模式各跑 5 次，指标原始数据在 data/benchmark.json，可一键复现（py -3.14 scripts/benchmark.py）。在一次 12 节点的 AI4S 空气质量分析任务上：

模式 平均耗时 Token 消耗 置信度 关键系数误差 验证通过率
A 单 Agent，无验证 0.157 s 5,845 0.873 34.38% 0%
B 多 Agent 并行，无验证 0.386 s 21,309 0.890 34.38% 0%
C 多 Agent + 验证自循环 1.031 s 27,190 0.930 7.14% 100%

读数方式：模式 A/B 的“置信度 0.873/0.890”是模型自评口径——看起来很高，但关键系数误差 34.38%，说明自评置信度与真实正确性严重脱节；模式 C 通过独立复算与交叉验证把误差压到 7.14%，验证通过率从 0 提升到 100%。这正是本项目要证明的事：加验证不是加开销，而是把“看起来对”变成“算出来对”。

口径说明：以上为 Mock 确定性模型下的实测值，用于验证机制流程与相对差异；真实模型下的绝对值会不同，且受非确定性影响，需在真实环境中重新测量（见 3.6）。

3.2 场景覆盖

仓库内置 10 个行业场景工作流（8 个单目标 15 节点 + 2 个多目标 16 节点），覆盖 AI4S 科研分析、公共健康风险、制造质量根因、金融风控指标、能源负荷、教育评估、供应链、环境监测、医疗指标、市场调研等方向。批量回归命令 py -3.14 scripts/run_scenario.py --all --json 全部通过；其中公共健康场景首轮有两项检查失败、自循环第二轮通过，是验证机制按设计生效的直接证据，而非缺陷。

3.4 成本与效率（测算，非实测商用数据）

以“一份需要统计建模与结论复核的分析报告”为单位做粗算（假设参数见 4.6，均为估算而非实测账单）：

  • 人工方式：具备统计背景的分析人员 2–6 小时，按综合人力成本折算约 ¥320–¥1,200/份；
  • 本平台方式：一次运行约 2.7 万 Token（Mock 口径），接入真实模型后按主流 API 价格估算约 ¥13–¥25/份，另加人工审阅 10–20 分钟；
  • 关键差异不在单份成本，而在可复核性：人工报告的错误往往无人复算，而平台把复算、交叉验证、统计检验做成必过项，把“事后返工”成本前移。

3.5 用户价值的三层结构

  1. 工程复用层：把编排、调度、验证、自循环做成可复用的平台能力，新场景只需写工作流 JSON 与检查项配置，不必重写框架。
  2. 结果可信层：用独立复算与交叉验证把“模型自评”替换为“多源一致”，直接降低错误结论外流风险（基准中系数误差 34.38%→7.14%）。
  3. 合规审计层：事件流、调度理由、验证证据、产物归档构成可追溯证据链，可支撑内部评审与外部审计对“结论怎么来的”的追问。

3.6 尚未验证的部分（必须说清楚）

  • 真实大模型链路：OpenAI 兼容适配器已实现并有单元测试，但未用真实 Key 完成端到端生产运行；真实模型下的非确定性、超时、限流、成本波动尚未测量。
  • 真实业务数据：全部演示数据为合成数据；对真实数据的质量分布、异常模式、口径差异尚未验证。
  • 规模与长稳：仅验证了单机 8 路并发突发的准入正确性，未做长时间负载、内存增长、数百次运行的持久化压力测试。
  • 产品化能力：无多租户隔离、计量计费、SLA、告警与备份策略，当前形态适合试点与演示，不适合直接对外提供 SaaS。

四、商业模式

4.1 客户与付费方

我们不与通用 Agent 平台争夺“人人都能搭 Agent”的市场，而是选择“必须为分析结论负责”的客户作为切入点：

客户群 典型场景 付费方 切入理由
高校 / 科研院所课题组（首选） 数据清洗、统计建模、结论复核、论文/报告数据一致性检查 课题组经费、学院信息化预算 对“可复现、可审计”有刚性要求；预算小额、决策链短；与团队所在院校有天然接触面
制造企业研发 / 质量部门 质量根因分析、工艺参数与缺陷关联、检测报告生成 质量或研发部门预算 报告需要可追溯证据链；重复性高，适合模板化场景包
第三方检测 / 咨询机构 多源数据汇总、指标核算、报告批量生成与自检 机构运营预算 报告量大、格式固定、错误代价高（返工与信誉损失）

4.2 价值主张

对客户的一句话：“同样的分析，我们能给出结论，也能给出结论的证据链。”

可量化收益（以报告类工作计，均为测算口径）：

  • 单份报告的机器成本约 ¥13–¥25（真实模型价，按 2.7 万 Token 估算），相对人工 2–6 小时的 ¥320–¥1,200 显著下降；
  • 复核环节从“人工抽查”变为“机器必检 + 人工终审”，把主要返工点前移，减少返工工时；
  • 结论留痕：调度理由、验证证据、产物版本可追溯，降低审计与复盘成本。

4.3 收入模式

采用“软件授权 + 场景包 + 服务”的组合，避免单一项目制：

收入类型 形态 说明
私有化部署授权 按年授权（单机 / 部门级） 客户数据不出内网，符合科研与制造客户的安全诉求；含平台核心与基础检查器库
场景包订阅 按场景 / 按年 面向具体业务的场景模板：工作流 JSON + 检查项配置 + 数据契约 + 报告模板
实施与定制服务 项目制 真实数据接入、口径对齐、检查器定制、部署与培训
托管 SaaS（远期） 订阅制 在多租户、计量、SLA 能力具备后提供，不作为近期收入来源

4.4 定价假设（明确标注为假设，尚未市场验证）

项目 假设价格 依据与说明
单机私有化授权 ¥2–5 万 / 年 对标国内同类数据分析/低代码工具的部门级授权区间，属估算
场景包 ¥1–3 万 / 场景 / 年 含模板、检查项与一次口径对齐服务
实施服务 ¥1,000–1,500 / 人天 按本地软件实施服务常见区间估算
托管版（远期） ¥300–800 / 席位 / 月 待产品化能力具备后再验证

定价原则：先卖“可审计的报告能力”（价值可被算清），再卖“平台”（复用价值更高但决策链更长）；首单以场景包 + 实施切入，验证价值后再扩授权。

4.5 成本结构

  • 研发成本为主：平台与检查器库的持续研发是主要投入；当前为单人团队，边际人力成本低但不具备规模化交付能力。
  • 交付成本低：零第三方运行时依赖、单机部署，客户侧硬件要求低（普通办公电脑/服务器即可）。
  • 模型调用成本随用量线性增长：真实模型下的 Token 成本是主要变动成本；可通过小模型路由、结果缓存、按需验证深度控制。
  • 服务成本：实施与口径对齐需要领域人力，是早期毛利率的主要拖累项。

4.6 单位经济测算（示例，含全部假设）

以“客户一年 200 份分析报告”的小型部门为例：

项目 测算
人工基线 200 份 × ¥600（中位估算）= ¥12 万 / 年
平台授权 ¥3 万 / 年（假设）
模型调用 200 份 × ¥20 = ¥4,000 / 年
人工终审 200 份 × 0.3 小时 × ¥200 = ¥1.2 万 / 年
客户侧总成本 约 ¥4.6 万 / 年，相对基线节省约 ¥7.4 万 / 年（约 62%）

以上为客户侧视角的粗略测算，参数均为假设值，不构成收益承诺；真实节省取决于报告复杂度、模型价格与人工审阅强度。

4.7 获客渠道

  1. 校企合作（近期主渠道）：以院校课题组为第一批试点，用真实（脱敏）数据验证检查器与场景包，形成可公开的案例与评测记录。
  2. 行业集成商 / 咨询机构（中期）：把平台作为其报告生产线的质量层，按项目分成或授权转售，借助其客户关系降低获客成本。
  3. 开源引流（长期）：仓库以可复现、可评审形态开放（代码与文档齐全），以“可验证的 Agent 工程实践”建立技术信任，再将企业版能力（场景包、检查器定制、部署支持）商业化。
  4. 竞赛与学术曝光：通过本赛事、院校交流与论文/技术分享触达目标客户群。

4.8 竞争壁垒

  • 机制壁垒：13 个检查器 + 五层验证漏斗 + 结构化反馈驱动的自循环，是一套被测试与基准固化的工程组合，而非提示词技巧；
  • 契约壁垒：Agent 岗位定义、工作流 DSL、事件契约、产物规范均已文档化（CONTRACTS.md），可被客户与集成商按其口径扩展，迁移成本随使用加深；
  • 评测壁垒：可复现的 A/B/C 基准与 10 场景回归，使“验证是否真的有效”可被第三方复算，而不是自说自话；
  • 审计壁垒：调度理由与验证证据全量留痕，契合科研与制造客户对“结论怎么来的”的合规诉求。

4.9 里程碑（假设时间表）
