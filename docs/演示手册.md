# 现场演示手册 · 织流 AgentWeave

> 用途：5 分钟现场演示 / 4 分钟录屏 / 答辩现场复现。所有数字均来自本机真实运行，可用一条命令重跑。
> 配套：[演示回放（离线 HTML）](../demo/演示回放.html) · [演示实录（终端逐事件）](演示实录.md) · [视频脚本](视频脚本.md)

---

## 0. 一页纸主张（背下来）

> **多智能体不缺 Demo，缺的是「证明它做对了」的工程环节。**
> 我们把编排、调度、验证、自循环做成可执行的资产：
> **流程是数据（可改）、调度有理由（可查）、结果是证据（可验）、失败会自愈（可控）。**
> 现场这条链路：12 个节点、7 个 Agent、2 条并行分支、1 个五层验证、1 个 PDCA 自循环——
> 首轮置信度 42.3% 被判失败，系统自己定位到「wind 系数偏差 37.2%」，注入结构化反馈后重跑，
> 第二轮 100% 通过，全程 0.6 秒、27,191 Token、84 条事件全部可回放。

## 2A. 用户视角演示（3 分钟，最推荐）

> 这是普通用户打开网站后的视角：不接触 DAG、事件流等工程概念，只做「选任务 → 看结论」。

### 0:00–0:20 总览仪表盘（场景入口）

**操作**：打开 http://127.0.0.1:8765，停在场景列表。

**讲**：
> 「打开网站，第一眼不是一个 Agent 聊天框，而是**可分析的任务目录**：11 个场景，覆盖科研、零售、电商、制造、能耗、物流、教育、营销、公共卫生。
> 用户不需要懂编排，只需要选一个任务。」

**屏幕应显示**：hero 三步骤（选场景 / 一键运行 / 看结论与证据）、11 张场景卡、过滤器。

### 0:20–0:40 选一个多目标场景

**操作**：点右上角「多目标联合」，点「制造质量-能耗联合分析」卡片 → 看弹层信息 → 点「开始运行」。

**讲**：
> 「这个场景同时分析两个目标：良品率和单位能耗。弹层先告诉用户数据规模、目标、流程节点和验证方式，再让他确认。」

### 0:40–1:20 运行与进度

**操作**：等进度条走完（约 1 秒），看「正在执行」节点名与 Token 累计。

**讲**：
> 「后台在跑 16 个节点：规划、扫描、并行调研、清洗、修复循环、统计建模、验证、稳健性、敏感性、联合对比。
> 用户看到的只是进度和耗时，复杂编排被平台收起来了。」

### 1:20–2:20 结果弹层：结论 + 证据

**操作**：结果弹层出现后，依次指 KPI、验证过程、报告摘录。

**讲**：
> 「结果不是一句『分析完成』：最终置信度 93%、验证 2 轮——第 1 轮 42%，验证器发现系数偏差，自动触发修复；第 2 轮 100% 通过。
> 下方是报告摘要和联合结论。点『下载报告』可拿到完整 Markdown，点『查看完整证据』跳到「运行与验证中心」看五层检查明细。」

### 2:20–3:00 再做一次 / 最近任务

**操作**：关闭弹层，展示「最近任务」，点一条历史记录直接回到结果。

**讲**：
> 「所有运行都可回看、可分享（`/?run=<id>` 直接打开结果）。这就是从『能演示』到『能交付』的差别。」

## 2B. 工程视角演示（5 分钟，适合技术评委）

### 0:00–0:30 概览页：先给结论

**操作**：停在概览页，鼠标指三个数字。

**讲**：
> 「7 个 Agent、1 条工作流、平均置信度 93%。注意，置信度不是模型自评，是五层验证算出来的。
> 今天只演示一件事：**一份多智能体产出的科研结论，怎么被证明是对的。**」

**屏幕应显示**：Agent 7 · 工作流 1 · 运行数 ≥1 · 平均置信度 93.0%。

### 0:30–1:15 流程编排中心：流程是数据

**操作**：点左侧「流程编排中心」，鼠标沿 DAG 从左到右划一遍；在 `PDCA 自循环` 和 `可验证` 节点各停 2 秒。

**讲**：
> 「12 个节点不是代码写死的：它是 JSON DSL，可进 Git、可评审。
> 这两条是并行分支——数据扫描和方法调研同时跑；
> 这个橙色回环是 PDCA 自循环：验证不过就回到修复节点，最多 3 轮，无改善即停；
> 最后是人工闸门，发布报告前必须有人确认（演示模式自动放行）。」

**屏幕应显示**：12 节点、并行分支、PDCA 回环、人工闸门、`12 节点` 下拉。

### 1:15–2:15 运行与验证中心：看得见的调度与执行

**操作**：点「运行演示场景」→ 自动跳「运行与验证中心」；让它跑完（约 1 秒），然后**放慢讲**。

**讲**：
> 「看右边事件流：每一次派活都有 `node.scheduled`，带 score、候选和负载；
> 调度不是黑盒，是可以回放的决策记录。
> 看顶部：第 1 轮 42.3%——**验证失败了**。这不是 bug，是设计：首轮系数故意有偏差，用来展示闭环。
> 看左下：失败项 `code_rerun` 和 `numeric_ground_truth`，wind 申报 -1.05，真值 -1.6，偏差 34.4%。」

**屏幕应显示**：第 1/3 轮 42.3% 修复 → 第 2/3 轮 100% 通过；自循环 2 轮；12 节点；事件流持续滚动。

### 2:15–3:15 验证中心：失败也留下证据

**操作**：点「运行与验证中心」；先讲顶部 100.0%「最终通过」，再指右侧「自循环历史」两轮。

**讲**：
> 「验证不是问模型『你对吗』，是五层证据：
> 结构、真值比对、代码重跑、另一个 Agent 独立复算、统计显著性。
> 硬性失败一票否决，不会被平均分掩盖。
> 右边是两轮历史：第 1 轮 42.3%、失败项写清楚；第 2 轮 100%、提升 0.58。**每一轮都能复查。**」

**屏幕应显示**：环形 100.0% / 最终通过 / 共 2 轮验证 / 第 1 轮 42.3% 失败项 / 第 2 轮 100%；五层表 4 项通过。

### 3:15–3:45 自循环：失败如何被修好

**操作**：回「运行与验证中心」，指顶部两轮徽标；或打开 `data/runs/<run_id>/report.md` 的验证轨迹段。

**讲**：
> 「关键在反馈内容：不是『再试一次』，而是『哪一项失败、期望多少、实际多少、偏差多少』。
> 反馈注入修复节点，定向重跑；第二轮系数修正为 -0.84/0.44/-1.67/0.26，进入 15% 容差。
> 有轮次上限、有收敛判据、有停止理由（converged），不会无限重试烧钱。」

### 3:45–4:30 报告 + 基准：价值落地

**操作**：讲 `report.md`（分节：数据与方法 / 主要发现 / 验证证据 / 局限与建议 / 结论），或切 PPT 第 11 页基准表。

**讲**：
> 「产物不是一句回答，是一份可复核报告 + 代码 + 指标 + 事件流，全在 run 目录里。
> 最后看成本：单 Agent 0.16 秒但误差 34.4%、0 验证；多 Agent 并行 0.39 秒，误差不变；
> 加上验证与自循环 1.03 秒、Token +27.6%，换来误差 7.1%、验证通过率 100%。
> **我们不宣称全面更优——我们卖的是『可接受成本换可验证的正确性』。**」

### 4:30–5:00 收尾

> 「所以 AgentWeave 补的不是又一个框架，而是四道工程鸿沟：可编排、可解释、可验证、可自愈。
> 一句话：**可验证，才是可交付。**」

## 3. 路线 B：终端演示（3 分钟，适合录屏/网络不稳）

```bash
py -3.14 scripts/demo_tour.py
```

**为什么这条路线有说服力**：终端直接打印事件总线原文——规划、派发（含 score）、验证失败明细、反馈注入、第二轮通过、系数对比表。评委能看到「不是页面动画，是引擎真的在跑」。

**讲解节奏**：
1. 看到 `② 启动` → 讲 DAG 拓扑与并行分支；
2. 看到 `③ 验证-1 失败 · 置信度 0.423` → 停下讲五层验证与硬性失败；
3. 看到 `④ 自循环-1` +「反馈注入修复节点」→ 讲结构化反馈；
4. 看到 `③ 验证-2 通过 · 1.000` → 讲收敛判据；
5. 最后看「系数对比表」：首轮 -1.05 → 第二轮 -1.67 → 真值 -1.6。

## 4. 应用价值：三条可量化的证据

| 评委关心 | 证据（本次实测） | 现场指哪里 |
|---|---|---|
| 结果是否可信 | 首轮 42.3% → 修复后 100%；系数偏差 37.2% → ≤7%；四层检查全部留证 | 运行与验证中心的两轮历史 + 五层表 |
| 调度是否可解释 | 14 条 `node.scheduled`，每条含 agent/score/负载；87 条事件可回放 | 运行与验证中心左侧「调度决策」+ 事件流 |
| 失败能否自愈 | 2 轮 PDCA，无需人工；有 max_iterations=3、stagnation 判据、converged 停止理由 | 顶部轮次徽标 + report 的「自循环统计」 |
| 能否迁移到别的任务 | 工作流是 JSON DSL；7 个 Agent 角色配置化；工具注册表热插拔；换模型只改配置 | 流程编排中心 + 配置文件 + 系统配置页 |
| 成本是否可接受 | 0.6–1.0 s/次、约 2.7 万 Token；对比 A/B 模式量化「验证的溢价」 | 基准表 / `data/benchmark.json` |

## 8. 评委追问三连（30 秒版）

1. **「验证器也是 LLM 吗？会不会自证？」**
   → 不是。L3 是真跑代码复算（子进程 + 输出比对），L4 是另一个 Agent 用同一数据独立重算；Mock 模式下验证者不共享统计师的输出。LLM 评审只是可选的 L5，默认关闭。
2. **「这不就是 prompt 编排吗？」**
   → Prompt 只是节点配置的一小部分。真正的工作量在：DAG 引擎（并行/条件/循环/子流/人工闸门）、可解释调度、五层验证、自循环收敛与预算、事件总线可回放、零依赖可复现。任何一条都不是 prompt 能替代的。
3. **「换一个课题要改多少？」**
   → 换数据 + 改工作流 JSON（数据路径、分析提示、验证阈值）即可；Agent 与工具通过配置注册，引擎不改。演示数据与真值是分离的，真值只有验证器可见。
