===== S1  钩子  =====
多智能体不是把几个 Agent 串起来。真正的难题是——七个 Agent 交出一份报告，你凭什么相信它是对的？我们做了一个平台，专门回答这个问题。

===== S2  痛点与方案  =====
今天的大多数 Agent 作品，卡在四道鸿沟上：流程写死在代码里，换个任务就得改程序；调度是个黑盒，为什么选这个 Agent 没人说得清；结果说完成了，却无法验证数字对不对；失败之后只会重来，不知道有没有变好。我们把这些环节做成平台能力：声明式编排、可解释调度、五层验证，加上一个带预算的修复闭环。

===== S3  启动与编排台  =====
一条命令启动，纯 Python 标准库，不装任何依赖，断网也能跑。这是编排台：左边是流程画布，节点、并行分支、循环回边一目了然；点开任意节点，能看到它的 Agent、工具、输入输出映射和验证规约。整套流程保存为一份 JSON，可以进版本库、可以被评审。

===== S4  运行与实时事件  =====
点击运行。所有节点状态通过 SSE 实时推送到前端。这里可以看到调度器的每一次决策：候选是谁、得了多少分、为什么选它。数据扫描和文献调研两个分支并行执行，互不阻塞。注意这一行——统计建模师的输出已经出来了，但系统没有直接采信，而是把它交给验证流水线。

===== S5  验证失败与自循环  =====
第一轮验证失败：数值检查发现最大系数偏差 34.4%，超过 15% 的容差。关键在于，系统给出的不是一句「再试一次」，而是结构化反馈：哪一项失败、期望值多少、实际值多少、偏差多少。这份反馈被注入修复节点，定向重跑。第二轮，偏差进入容差，五层全部通过，置信度达标。整个修复过程有轮次上限和收敛判据，不会无限重试。

===== S6  架构：控制面与执行面  =====
架构上，我们把控制面和执行面彻底分开。工作流引擎、调度器、验证流水线在控制面；Agent 运行时、工具沙箱、模型客户端在执行面。引擎只能通过一层上下文接口去调用它们，不直接依赖任何模型实现。好处很直接：引擎可以被单元测试，模型可以被整体替换，Mock 和真实大模型走同一条路径。

===== S7  算法：调度与五层验证  =====
调度不是一个黑盒。我们把五种策略统一到一套加权打分上，每次决策都留下分数、理由和负载，可以回放、可以调参、可以被度量。验证则是五层漏斗：结构对不对、数值对不对、代码能不能复现、另一个 Agent 独立复算是否一致、统计上是否显著。任何一项硬性检查失败，直接一票否决，不会被平均分掩盖。跳过项不计入分母，置信度不会虚高。

===== S8  价值收尾  =====
最后，一份带图表和指标的 Markdown 报告自动生成，所有中间产物都落在 run 目录里，可以复查、可以对比。基准测试里，加了验证与自循环会多花时间和 Token，但误差显著下降、置信度可量化——这就是我们愿意付的代价。织流 AgentWeave：可编排，可解释，可验证。可验证，才是可交付。
