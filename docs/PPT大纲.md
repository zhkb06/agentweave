## 第 2 页 · 痛点：多智能体卡在「演示」与「生产」之间

**标题**：Demo 很惊艳，落地很狼狈：四道工程鸿沟

**上屏要点**
1. **流程硬编码**：换任务就要改代码，编排无法被非开发者复用
2. **调度黑盒**：为什么选这个 Agent？没人说得清，出错只能猜
3. **结果不可验证**：模型说「已完成」，没人知道数字对不对
4. **没有反馈闭环**：失败就重来，重来几次、是否变好，全凭感觉
5. 科研场景代价更高：一次错误归因，可能误导后续全部实验

**配图说明**：四象限图，四格分别写「硬编码 / 黑盒调度 / 不可验证 / 无闭环」，中心写「Demo → 生产」的断崖。用暖橙标注「断点」。

**讲者备注**：强调这不是「框架不够多」，而是「工程环节缺失」。落一句过渡：「所以我们做的不是又一个 Agent 框架，而是补齐这四块。」

## 第 3 页 · 方案总览：一个平台，五个能力，一条闭环

**标题**：AgentWeave：把编排做成可执行、可解释、可验证的资产

**上屏要点**
1. 五大模块：Agent 定义 · 工作流编排 · 调度执行 · 验证监控 · 反馈优化
2. 一条主链路：**声明式工作流 → 可解释调度 → 五层验证 → PDCA 自循环 → 报告**
3. 人只写「做什么」，系统负责「谁来做、做得对不对」
4. 交付形态：Web 控制台 + REST/SSE + 命令行，三种入口同一内核
5. 离线确定性演示，亦可一键接入真实大模型

**配图说明**：横向五段流水线箭头图，每段一个图标；箭头下方用一条回环曲线标出「验证失败 → 反馈注入 → 重跑」。

**讲者备注**：这一页只讲结构不讲细节，让评委建立「五个能力 + 一条闭环」的整体印象。提醒自己：闭环是全场主角。

## 第 4 页 · 总体架构：六层分离，控制面与执行面解耦

**标题**：六层架构：引擎不碰模型，模型不碰状态

**上屏要点**
1. L6 展示层：原生 JS/SVG 控制台，无构建、无 CDN
2. L5 接口层：REST + SSE，事件可断线续传
3. L4 控制面：工作流引擎、调度器、验证流水线、自循环控制器
4. L3 执行面：Agent 运行时、工具沙箱、MCP 客户端
5. L2/L1：事件总线、表达式求值、类型与配置资产
6. 铁律：引擎只经 `RuntimeContext` 调 Agent/工具，**不直接依赖 LLM 与工具实现**

**配图说明**：六层色块矢量图（PPT 第 4 页已绘制），右侧竖向箭头 + 「单向依赖」标注。

**讲者备注**：重点讲「解耦带来可测试性」——引擎可以被单测，模型可以被替换。若评委追问，指向 `RuntimeContext` 这一层。

## 第 5 页 · Agent 团队：七个岗位，各司其职

**标题**：不是七个聊天机器人，是一支有岗位说明书的团队

**上屏要点**
1. 规划者（0.2）拆任务 → 调研者（0.3）找方法 → 数据工程师（0.2）清洗
2. 统计建模师（0.1）出数与代码 → **验证者（0.0）独立复算**
3. 评审者（0.4）挑风险 → 撰写者（0.5）成文
4. 温度分层：越靠近「判断与事实」，温度越低
5. 每个角色都有：输入契约、输出 Schema、工具白名单、成功判据
6. 冲突消解四级升级：证据优先 → 交叉复算 → 评审仲裁 → 人工闸门

**配图说明**：七张角色卡片围成环，卡片内写「id / 温度 / 工具数」；中心写「证据优先」。可用团队合照式排版。

**讲者备注**：强调「验证者温度 0.0、无写权限」是设计而非巧合——防止「自己改题自己判卷」。这是最容易被记住的设计细节。

## 第 7 页 · 调度算法：每一次派活都给得出理由

**标题**：可解释调度：分数、理由、负载，一次决策三样都留下

**上屏要点**
1. 五策略：FIFO · 轮询 · 能力匹配 · 负载感知 · 自适应
2. 统一打分：`score = 能力×0.40 + 空闲×0.30 + 优先级×0.20 + 历史成功率×0.10`
3. 决策输出 `score / reason / agent_load`，前端可回放候选集
4. 自适应 = 能力匹配 + 负载惩罚 + 失败率修正，冷启动自动退化
5. 三层并发控制：节点并发 4、Agent 并发 2、失败重试 2 次后回退 Mock

**配图说明**：`screenshots/03-monitor.png` 左下「调度决策」面板（score 分项与 agent_load）+ 右侧公式卡片。

**讲者备注**：正面回答「凭什么是创新」——创新不在公式复杂度，而在「调度结果是可审计对象」。可现场问评委：「您希望系统告诉您为什么选它吗？」

## 第 8 页 · 五层验证：不信模型，只信证据

**标题**：五层验证漏斗：从「格式对」到「统计上可信」

**上屏要点**
1. L1 结构与非空 → L2 数值对齐真值（相对误差 ≤15%）
2. L3 代码重跑复现 → L4 跨 Agent 独立复算
3. L5 统计显著性与评审模型打分
4. 加权置信度 + **硬性失败一票否决**，跳过项不计入分母
5. `passed = 置信度 ≥ 阈值 且 无硬性失败`——不给「平均分掩盖致命错」留口子

**配图说明**：五层漏斗/阶梯图，标注每层「成本 / 是否硬性」；右侧一块「置信度计算」示例卡（含跳过项）。

**讲者备注**：重点讲 L4 交叉验证与「一票否决」，这是防幻觉的核心。别陷入权重细节，留到答辩。

## 第 9 页 · 自循环案例：首轮失败，如何被修好

**标题**：一次真实的失败修复：从 0.62 到通过，只用了两轮

**上屏要点**
1. 首轮：统计建模师漏控 SO₂，系数偏差超容差 → 验证失败（置信度 42.3%）
2. 反馈不是「再试一次」，而是「哪项失败、期望多少、实际多少、偏差多少」
3. 反馈注入修复节点，定向重跑；每轮记录签名，**无改善即停**
4. 第二轮：补齐控制变量，误差进入容差，置信度 100%，通过
5. 全程可回放：每轮事件、代码、指标都留痕

**配图说明**：`screenshots/04-verify.png`（100.0% 最终通过 + 自循环历史：第 1/3 轮 42.3% 失败 → 第 2/3 轮 100%）。左侧配 PDCA 小状态机。

**讲者备注**：这是全场最有说服力的一页，讲慢一点。强调失败是「设计出来的」——演示数据首轮必然偏差，才能展示闭环。

**标题**：从一句话任务到一份可验证报告

## 第 11 页 · 基准数据：三种模式，三种代价

**标题**：并行换来速度，验证换来确定性

**上屏要点**
1. 对照：单 Agent 串行 / 多 Agent 并行 / 并行 + 验证自循环
2. 指标：耗时、成功率、置信度、系数相对误差、Token
3. 单 Agent 最快但不可验证；并行缩短墙钟但不管对错
4. 加验证后耗时与 Token 上升，误差显著下降、置信度可量化
5. 数据来自 `docs/benchmark.json`，一条命令可复现

**配图说明**：已实测：A/B/C 耗时 0.157 / 0.386 / 1.031 s，最终误差 34.38% / 34.38% / 7.14%，置信度 87.3% / 89.0% / 93.0%，Token 5,845 / 21,309 / 27,190。数据来自 `data/benchmark.json`，`scripts/benchmark.py` 一条命令可复现。

**讲者备注**：务必诚实——不要宣称「全面更优」。落点是「用可接受成本换取可验证的正确性」，这句话评委会认可。

## 第 12 页 · 创新点：五点差异化

**标题**：五个工程取舍，让多智能体「可交付」

**上屏要点**

5. **零依赖离线可复现**，评委断网也能跑

**配图说明**：五宫格，每格一句「别人 / 我们 / 为什么更好」的浓缩版；配色统一，避免信息过载。
