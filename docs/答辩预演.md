## Q1 为什么不用 LangGraph / CrewAI 这些成熟框架？重复造轮子吗？

**一句话结论**：因为它们解决的是「怎么编排」，而我们解决的是「编排之后怎么保证算对」，后者的调度、验证、自循环在现有框架里都不是一等公民。

**展开**：
1. 我们的目标不是再做一个编排库，而是补齐四道工程缺口：硬编码流程、黑盒调度、结果不可验证、无反馈闭环。LangGraph 的图执行、CrewAI 的角色协作，主要解决第一项的「表达」问题，另外三项基本留给使用者自己写。
2. 平台需要**零依赖、离线可复现**：这是评审能在断网机器上跑通的前提。引入第三方框架会带来依赖树、版本兼容和联网安装问题，与我们的硬约束冲突。
3. 我们的核心抽象只有一层：`RuntimeContext`。引擎只经它调 Agent 与工具，不直接依赖模型实现。这意味着**将来完全可以把 LangGraph 当作某一层的执行后端接进来**，而不是二选一。
4. 事实层面，我们的 `core/types.py`、`core/expr.py` 已有真实实现与单测，不是 PPT 上的架构。

**加分补充**：可以现场打开 `agentweave/core/types.py` 展示节点、边、验证规约的类型定义，说明「契约先行、可被替换」。

**可能追问**：*你们的引擎有 LangGraph 的 checkpoint 能力吗？* → 有 `RunState.snapshot/rollback` 与事件回放，但粒度是节点级，不是每步 token 级；这是有意的取舍（成本 vs 回放精度）。

## Q2 调度算法就是几个权重相加，凭什么说是创新？

**一句话结论**：创新不在公式复杂度，而在于把「调度决策」从不可见的实现细节，变成可解释、可回放、可度量的一等对象。

**展开**：
1. 多数框架的调度是固定映射或轮询，决策过程在黑盒里；出问题只能翻日志猜。我们把五策略统一到一套加权打分：`score = 能力×0.40 + 空闲×0.30 + 优先级×0.20 + 历史成功率×0.10`，每次输出 `score / reason / agent_load`。
2. 这个 `reason` 不是给人看的日志，而是**产品能力**：前端可以回放候选集、展示分项贡献；测试可以断言决策结果；基准可以比较策略优劣。也就是说，调度第一次可以被「评审」。
3. 工程上有真实约束：三层并发控制（节点 4 / Agent 2 / 失败重试 2 次后回退 Mock）、同分时用稳定排序保证确定性、自适应在冷启动时退化为能力匹配、并按全局成功率自动调权。
4. 我们的立场很明确：不追求「更聪明的算法」，追求「**可问责的算法**」。科研与生产场景里，能解释为什么选它，比多快 5% 更重要。

**加分补充**：现场提问「您觉得调度器应该告诉您理由吗？」——把评委带入我们的价值判断。

**可能追问**：*权重怎么定？* → 默认值在配置中，`adaptive` 用运行样本修正；方案书 6.3 有默认权重表，且 `describe()` 暴露当前权重，可调可查。

## Q3 你们怎么防止 LLM 幻觉？验证者自己也是 LLM，它错判怎么办？

**一句话结论**：我们不依赖「模型自评」，而是把验证拆成五层，其中三层是**可复算的客观检查**，且硬性失败一票否决。

**展开**：
1. L1 结构与非空：Schema 校验，客观。
2. L2 数值对齐真值：与数据集生成时的真值比对，相对误差 ≤15%（容差可配），客观。
3. L3 代码重跑：用独立进程重跑建模代码，看结果是否复现，客观。
4. L4 跨 Agent 独立复算：由验证者角色**重新实现**一遍计算并比对，这一层才涉及模型，但比的是数字不是措辞。
5. L5 统计显著性与评审打分：n≥1000、R²≥0.55 等硬阈值 + 评审模型给风险意见，权重最低。
6. 置信度 = Σ wᵢsᵢ / Σ wᵢ，**跳过项不计入分母**（避免离线无评审时虚高）；任一硬性检查失败直接不通过，防止「平均分掩盖致命错误」。

**加分补充**：验证者温度设为 0.0、且没有写文件权限——从设计上防止「自己改题自己判卷」。这是我们最容易被记住的细节。

**可能追问**：*L4 的两个 Agent 用同一个模型，相关性太高怎么办？* → 承认这是局限；缓解是它比的是数值而非文本，且 L2/L3 不依赖模型。后续计划接入异构模型做交叉验证（方案书 11.2）。

## Q4 自循环会不会死循环？会不会越修越差？

**一句话结论**：不会。我们设了六类终止条件，其中「无改善即停」和「预算上限」专门用来防止空转与劣化。

**展开**：
1. 轮数上限：`max_iterations` 默认 3，最坏情况成本可预估。
2. 预算上限：总步数、调用次数、时间任一触顶即停（`max_steps=500`）。
3. 收敛判据：置信度达标即停。
4. **无改善即停**：每轮记录失败签名（失败项 + 偏差方向），若连续两轮签名相同或置信度不升，判定无改善，停止并交人工。
5. 重复检测：同一修复动作重复出现即终止。
6. 用户取消：运行中可随时取消，1 秒内停止派发新节点。
7. 反馈是**结构化定向**的：失败项、期望值、实际值、偏差、建议，注入修复节点的 `feedback` 变量，而不是笼统「再试一次」。这让「越修越差」的概率显著降低；即使发生，轮次上限也兜底。

**加分补充**：演示场景首轮必然失败、第二轮通过，正是因为反馈指明了「漏控 SO₂」，而不是随机重试。

**可能追问**：*如果三轮都失败呢？* → 标记为「需人工介入」，保留全部轮次证据（代码、指标、事件），人工闸门节点接管。失败也是可交付的结论。

## Q5 性能数据呢？加验证是不是很慢？

**一句话结论**：离线演示端到端 ≤8 秒，SSE 首事件 <500ms；加验证确实更慢，但我们把它当成「可接受的成本」而非缺陷。

**展开**：
1. 硬指标（契约中定义）：离线 Demo ≤8s、SSE 首事件 <500ms、200 次连续运行内存不失控（事件缓冲上限 4000）。
2. 基准对照三模式：单 Agent 串行 / 多 Agent 并行 / 并行 + 验证自循环。并行分支（数据扫描与文献调研）缩短墙钟时间；验证与自循环带来额外耗时与 Token。
3. 我们的结论不粉饰：**C 模式（带验证）不是所有维度最优**，它用可接受的成本换取可验证的正确性与可量化置信度。生产系统愿意为「知道对不对」付费。
4. 实测数字见 `data/benchmark.json`，脚本 `scripts/benchmark.py` 可复现；所有原 `[[待测]]` 项均已回填，未测的边界在方案书中明确标注。

**加分补充**：主动说明「如果评委要求更快，可以关掉 cross_agent 与 llm_judge，用 L1–L3 兜底，耗时显著下降」——体现可配置性。

**可能追问**：*8 秒怎么测的？* → 5 次取中位数，脚本输出原始数据；换机器以实测为准。

## Q6 和 LobeHub、DSH 这类产品/工具有什么区别？

**一句话结论**：它们优化「单个或一群 Agent 的使用体验」，我们优化「任务级结果的可问责性」。

**展开**：
1. LobeHub 类是 Agent 应用与市场：强在角色、插件、对话体验，面向个人生产力；多 Agent 协作偏「对话协商」，缺少任务级的验证与预算控制。
2. DSH 类是单 Agent 的执行 harness：强在工具调用与编码任务闭环；它管一个 Agent 如何把活干完，不管「一组 Agent 如何分工并对结果负责」。
3. AgentWeave 的对象是**工作流**：声明式 DAG + 可解释调度 + 五层验证 + PDCA 自循环 + 事件回放。我们不比谁更会用模型，比谁更能证明结果对。
4. 生态上我们不做封闭：MCP 客户端可接外部工具，OpenAI 兼容接口可接任意模型；定位是「编排与验证层」，可以与上述产品共存。

**可能追问**：*那你们有 LobeHub 的插件生态吗？* → 没有，也不打算做市场；我们做的是「可被集成的内核」。

## Q7 真实大模型怎么接？接了还能复现吗？

**一句话结论**：两种方式（环境变量 / Web 设置页）即可接入任意 OpenAI 兼容接口；接入后复现性会下降，所以我们把 Mock 作为默认，把真实模型作为可选项。

**展开**：
1. 配置项：`provider / base_url / model / api_key`，Key 支持环境变量 `AGENTWEAVE_API_KEY`，也可在设置页输入（password 框，保存后不回显、不写入前端存储）。
2. 兼容性：OpenAI 兼容协议，DeepSeek、通义千问、智谱等可直接用；`config/platform.json` 里有超时 60s、重试 2 次、失败回退 Mock 的默认值。
3. 路由：`smart/fast` 两级，规划者/统计建模师/验证者走 smart，评审与默认走 fast，控制成本。
4. 复现性：真实模型有非确定性，同一提示两次结果可能不同。因此演示默认 Mock（固定种子、逐字节可复现），真实模式靠温度分层（验证者 0.0）、结构化输出与验证兜底来降低波动。这个取舍我们在方案书第十一节明确写了。

**可能追问**：*演示为什么不用真实模型？* → 断网可跑是硬要求；真实模型作为可选能力演示时另录一段，两套都展示。

## Q8 数据隐私怎么保证？会不会把数据传到外部？

**一句话结论**：默认零外传——Mock 模式全本地、无网络；只有你主动配置真实模型或 HTTP 工具时才会出网，且可完全关闭。

**展开**：
1. 离线模式：`provider=mock`，不发起任何外部请求；演示数据是本地生成的合成数据，不含任何真实个人信息。
2. 出网面收敛：只有三类可能出网——真实 LLM 调用、`http_get` 工具、MCP 远程服务。三者都需要显式配置；`mcp_servers` 默认为空。
3. 密钥处理：Key 走环境变量优先；接口返回一律打码；前端不持久化明文。
4. 工具沙箱：`file_read/file_write` 限制在工作目录内，路径穿越（如 `../../`）被拒绝并报错；`python_exec` 有超时与输出上限。
5. 数据资产：演示数据集与真值文件都在仓库内，可审计来源与生成脚本。

**可能追问**：*企业内网部署可以吗？* → 可以，纯标准库、无外网依赖，天然适合内网；只需把真实模型指向内网网关。

## Q9 这个东西能商业化吗？谁会用？

**一句话结论**：最现实的切入点是「对结果正确性负责的科研与工程分析场景」，而不是通用聊天助手。

**展开**：
1. 目标用户：高校/科研院所的 AI4S 团队、企业研发中的数据分析与实验报告流水线、需要审计留痕的合规型分析。
2. 价值主张：把「分析过程」变成可复现、可审计、可追责的资产——报告附带验证证据与置信度，而不只是一段文字。
3. 形态：当前是开源内核 + Web 控制台；可演化为私有化部署的分析平台，按团队/项目授权。
4. 成本结构：零依赖降低部署成本；Token 成本可控（路由 + 检查项可裁剪）。
5. 诚实边界：目前是单机、合成数据验证，尚未做真实客户验证；商业化路径在方案书 11.2 有分阶段规划，不夸大。

**可能追问**：*和现成的数据分析平台比呢？* → 它们强在 BI 与可视化，我们强在「多 Agent 分工 + 自动验证 + 失败自修复」，是流程层而非展示层。

## Q10 如果两个 Agent 结论冲突、互相推诿怎么办？

**一句话结论**：冲突是设计内的，用四级机制消解：证据优先 → 交叉复算 → 评审仲裁 → 人工闸门。

**展开**：
1. **证据优先**：先比可复算的证据（代码、指标、复现结果），而不是比谁说得好。数值不一致就重跑。
2. **交叉复算（L4）**：由独立验证者重新实现计算，两方结果对比；差异定位到具体步骤。
3. **评审仲裁**：评审者（critic）读取双方输出与证据，给出风险清单与建议；它没有写权限，只能建议。
4. **人工闸门**：高风险或无法收敛时，`human_gate` 节点暂停，等人确认；`auto_approve` 仅用于演示场景。
5. 机制上防推诿：每个 Agent 有明确的输入/输出契约与成功判据，输出必须符合 Schema；验证失败会精确指向「哪个节点的哪一项」，责任无法模糊。
6. 升级路径还包含「重派」：若某 Agent 连续失败，调度器按失败率修正权重，把任务派给更合适的角色。

**加分补充**：这句话可以直接收尾——「我们的目标不是让 Agent 永不冲突，而是让冲突**可定位、可裁决、可留痕**。」
